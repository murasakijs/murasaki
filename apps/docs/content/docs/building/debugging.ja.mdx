`murasaki dev` は2つのものを同時に実行します。一方のprocessでは、Node Main
lifecycleをpluginとして読み込んだVite dev serverが動き、もう一方ではmain
thread上でnative WebView hostが動きます。それぞれdebugの勝手が異なります。
このページではWebView / renderer、その中のReact tree、そして長寿命のNode
Main processを扱います。packaging、signing、起動の障害は
[トラブルシューティング](/docs/building/troubleshooting)を参照してください。

## WebViewのdevtools

`murasaki dev` はnative binary自体がdebug buildかrelease buildかに関わらず、
常にdevtoolsを有効にしてwindowを開きます。packaged appはその逆で、devtools
は常にcompileから除かれ、配布物でdevtoolsを再度有効にするconfig flagはあり
ません。

- **macOS** はWKWebViewを使用しており、devtools自体のUIを持ちません。
  Safariの Develop menu を有効にし(Safari → 設定 → 詳細 →
  **Show features for web developers**)、**Develop → \<あなたのMac\> →
  localhost** から、実行中のwindowへSafariのWeb Inspectorをattachします。
- **Windows** はWebView2を使用しており、Chromium自体のDevToolsを直接
  embedしています — windowを右クリックして **Inspect** を選ぶか、
  **F12** を押します。

右クリックがOSのnative menu(**Inspect**を含む)を開くのは、windowが
[`useContextMenu`](/docs/guides/context-menu)で独自menuを宣言していない
場合だけです。window全体のcontext menuを宣言すると、そのwindowの右クリック
はあなたのmenuを開くようになります。**F12**はWindowsではどちらの場合でも
動作します。Murasakiは自分で宣言したshortcutに一致するkeyだけをintercept
するため、該当しないkeyはそのままWebView2に届きます。

<Callout type="info">
  native bindingにはWebView objectの`openDevtools()`methodもありますが、
  Murasakiの現在のpublic APIはそれをどこからも呼び出していません。Node Main
  やrendererからprogrammaticにdevtoolsを開く手段は今のところありません。
  WebView自体の右クリックmenuかkeyboard shortcutを使ってください。
</Callout>

## browserでReact DevToolsを使う

`murasaki dev` はappをcustom protocolではなく実際のHTTP
(`http://127.0.0.1:<port>/`)で配信するため、native windowと並べて同じURL
をChromeで開けます。標準の **React DevTools** browser extensionは、他の
普通のpageと同様にattachします — 特別な統合は不要です。

ただし普通のbrowser tabはapp本体ではありません。`/api/*` と
`/__murasaki/*` はnative WebViewのsessionで保護されているため、その
Chrome tabからのServer Actions / API route呼び出しは正しく`403`になり
ます。React treeの確認にはtabを、app自体の動作確認にはnative windowを
使ってください。[Backend callが403](/docs/building/troubleshooting#backend-call-が-403)
を参照してください。

## dev error overlay

uncaught errorは、空白のwindowやconsoleだけのstack traceの代わりに、
murasakiブランドのfull-screen overlayとして表示されます。次の3つの
capture pathから供給されます:

- render error(error boundaryの`componentDidCatch`経由)
- uncaught exception(`window.onerror`経由)
- unhandled promise rejection(`unhandledrejection`経由)

overlayは常に最新のerrorを、そのstackと(render errorの場合は)React
component stackとともに表示し、badgeでqueueされている以前のerror数を
示します。連続する同一errorはdedupeされるため、React Strict Modeの
double-invokeやrepeat-renderでoverlayが同じerrorだらけになることはあり
ません。**Esc**または**Dismiss**buttonで閉じ、**Reload**でpageを再読み込み
します。production buildではno-opです — overlay全体がcompileから除かれ
ます。

## Node Mainをdebugする

Node Mainは`murasaki dev`が起動するdev-server processと同じprocess内で
Vite pluginとして動くため、`ready()`、`shutdown()`、または任意の
`'use main'`関数内の普通の`console.log`は、`murasaki dev`を実行した
terminalへそのまま出力されます。

`context.log`はこれとは意図的に異なります。そのterminalへは一切echoされ
ません。`log.info` / `warn` / `error` / `debug`の呼び出しはすべて、
JSON Linesとして`paths.logs/murasaki-main.jsonl`にだけ書き込まれ、5 MiB
でrotateし、過去5file(`.1`…`.5`)を保持します。構造化log出力をliveで見た
い場合は、そのfile(またはOSのlog viewer)をtailしてください:

| OS | `paths.logs` |
| --- | --- |
| macOS | `~/Library/Logs/<appId>` |
| Windows | `%LOCALAPPDATA%\<appId>\Logs` |
| Linux | `$XDG_STATE_HOME/<appId>/logs`(既定は`~/.local/state/<appId>/logs`) |

各行は`{ timestamp, level, message, fields? }`です。key名がcredentialに
見えるfield値(`authorization`、`cookie`、`password`、`secret`、`token`、
`apiKey`、`privateKey`など)は、書き込み前に`[redacted]`へ置き換えられ
ます。完全なredaction / size制限と、bound付きlog tail + application /
runtime metadataを1つの共有可能なJSON fileにまとめて`paths.logs/diagnostics/`
以下へ出力する`createDiagnosticReport()`については、
[Node Main → Logと診断report](/docs/guides/node-main#logと診断report)
を参照してください。

### Sidecarの出力

sidecarのstdout / stderrは
[`sidecar.onEvent()`](/docs/guides/node-main#同梱sidecarを監督する)
経由でしか届きません。各chunkは64 KiBで上限され、それを超えると
`…[truncated]`が付きます。また、`murasaki-main.jsonl`へ自動的に書き込ま
れることもありません。そこにも記録したい場合は、handler内で自分でlogして
ください:

```ts
indexer.onEvent((event) => {
  if (event.type === 'stderr') log.warn('indexer stderr', { output: event.data })
})
```

### packaged Windows appをdebugする

packaged appには既定で見える consoleがありません。`murasaki.config.ts`で
`window.console: true`を設定すると、Windowsでbackend Node console window
を表示できます — 一時的なCLI / debug出力に有用です。あるいは、起動後に
必要な情報は両platformとも`paths.logs`と`createDiagnosticReport()`に頼っ
てください。この releaseではNode Mainに`--inspect` debugger portは配線
されていません。`console.log`(dev時)と`context.log`が、現時点でsupport
されている手段です。

## よくある問題

- **portがすでに使用中。** `murasaki dev`は`config.devPort`(既定`5178`)
  を検査し、自動的に次の空きportへ進みます。
  [開発ウィンドウが開かない](/docs/building/troubleshooting#開発ウィンドウが開かない)
  と[`devPort`](/docs/building/configuration#トップレベルのフィールド)
  を参照してください。dev server自体が起動に失敗する場合は、
  `MURASAKI_DEBUG=1`を付けて再実行すると、branded一行の代わりに完全な
  stack traceが得られます。
- **WindowsでWebView2が無い / 古い。** MurasakiのWindows用WebViewは
  bundleされたChromiumではなく Microsoft Edge WebView2です。現行の
  WebView2 Runtimeが無い machineではwindowをまったくrenderできません。
  Windows 11とupdate済みのWindows 10の大半にはすでに入っていますが、
  そうでない場合は、他の何かをdebugする前にMicrosoftからEvergreen
  Runtimeをinstallしてください。
- **macOSで「壊れている」と表示される、または署名されていないbuildを
  Gatekeeperがblockする。** ad-hoc署名のdevelopment artifactでは想定内
  の挙動です。[トラブルシューティング](/docs/building/troubleshooting)
  のmacOS関連の項を参照してください。
